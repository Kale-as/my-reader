# 在线阅读器（PDF / EPUB 中英对照）

一个单文件网页阅读器：导入 PDF 或 EPUB 直接在浏览器里读，一边读原文一边看中文对照。

## 怎么用

直接用浏览器打开 `index.html` 就行，不需要 npm、不需要构建。

想部署到公网（Cloudflare Pages / Netlify / GitHub Pages / 自己的服务器）见
[DEPLOY.md](DEPLOY.md)：`node build-dist.mjs` 生成 `dist/`，拖上去即可。

如果双击打开（`file://`）时翻译一直跨域失败，用本地服务器打开：

```bash
cd 这个目录
python -m http.server 8000
```

然后访问 <http://localhost:8000/index.html>。

## 已经有的功能

| 能力 | 说明 |
| --- | --- |
| 导入 | 点「导入 PDF / EPUB」或把文件拖进窗口，支持一次多个 |
| 本地存储 | 文件存在浏览器 IndexedDB 里，不上传；书架记住阅读进度 |
| 英文阅读 | PDF 用 pdf.js 渲染（带文字层，可选词），EPUB 用 epub.js 分页渲染 |
| 中英对照 | 顶部的「对照」按钮三档切换：关 / 悬停 / 常显 |
| EPUB 对照 | 中文直接插在每一段英文下面，跟着正文排版、字号、主题走 |
| PDF 对照 | 把每页文字按行合并成段落，侧栏逐段对照，点条目会定位到页面上对应的位置 |
| 划词 | 选中任意英文，气泡里给整句译文，并可加入生词本 / 高亮 / 复制 |
| 生词本 / 高亮 | 各自独立存储，可点回原文位置 |
| 划词 | 选中英文后**不会自动翻译**，点「翻译」才请求；旁边 5 个色块可直接用它高亮 |
| 高亮颜色 | 5 种可选，记录里保存颜色，侧栏条目上带同色小圆点 |
| 阅读体验 | 字号、栏宽、亮色 / 米色 / 深色主题、背景色、选中文字颜色，键盘翻页（← →） |
| 滚轮 | 「外观」面板里可切换 滚动 / 翻页；Ctrl + 滚轮调整内容宽度（PDF 缩放 / EPUB 栏宽） |
| 侧栏 | 在左侧，拖动中间的分隔条可调宽度，宽度会记住 |

默认阅读方式是 **全文上下连续滚动**（EPUB 用 `scrolled-continuous`：整本书在同一个滚动流里，
不是每章一个独立滚动框），行距默认 1.9，侧栏默认展开。
顶部有页码框：直接输入页码回车即可跳转，两侧 `‹ ›` 是上一页 / 下一页。
顶部「设置」面板里可以调：字号、行距、栏宽、主题、背景色、选中文字颜色、高亮色、翻页方式、划选菜单。

高亮统一用半透明色 + `multiply` 混合，所以**不会盖住文字**；高亮层也排在文字下方。

### 关于滚动（为什么内容区没有独立滚动条）

内容区的滚动条是隐藏的（`.epub-container` / `.pdf-host` 的 `scrollbar-width: none`），
所以视觉上就是页面在滚，而不是嵌了一个小滚动框；当前位置看顶部页码 / 百分比。

底层仍然是 epub.js 自己的滚动容器，这一点不能改：试过把容器高度设为 auto、改由页面滚动，
结果是 epub.js 的进度追踪直接失效、而且它靠容器滚动决定"追加下一章"，整本书只会渲染出第一章。
所以正确做法是保留容器、去掉它的滚动条视觉，并让容器的高度严格等于可视区
（`relayout()` 在开关侧栏、拖分隔条、窗口缩放后都会重新量一次）。

另外，连续滚动模式下 epub.js 不一定发 `relocated` 事件，所以滚动后适配器会主动问一次
`rendition.currentLocation()` 来同步页码 —— 否则页码会在滚动时卡住。

划选菜单（选中文字后弹出的那个气泡）有三档：

| 档位 | 行为 |
| --- | --- |
| 自动弹出（默认） | 选中文字后立刻弹出 |
| 右键弹出 | 只有右键点击时才弹；没选中文字时右键仍是浏览器原生菜单 |
| 禁止弹出 | 完全不弹，避免干扰 |

点空白处、按 Esc 都会收起菜单。菜单里的「翻译」默认**不自动执行**，点了才会请求。
「设置」面板底部有「恢复默认」，也可以用 `?reset=1` 打开一次来清空所有阅读偏好。

## 翻译引擎

## 扫描版 PDF 的 OCR

扫描版 PDF（整页是图片、取不到文字对象）在阅读器里可以**就地 OCR**，不需要装任何东西：

| 能力 | 说明 |
| --- | --- |
| 引擎 | Tesseract.js（WASM，纯前端），**按需加载**：点了「识别」才下载内核和语言模型 |
| 语言 | 中英混合 / 英文 / 中文，可切换 |
| 触发方式 | 「识别本页」手动，或打开「自动识别」后随翻页自动识别当前页与前后各一页 |
| 结果缓存 | 识别结果按「书 + 页码 + 语言」存进 IndexedDB，同一页不会重复识别（第二次是毫秒级） |
| 识别之后 | 页面获得可选中文本层，段落进入「对照」面板，划词、翻译、高亮、生词本全部可用 |

实测：一本 85MB / 520 页的扫描书，第 6 页识别出 815 个词块、合并成 19 个段落，
置信度 92，首次约 16 秒（含语言模型下载），之后同页命中缓存是毫秒级。

### 识别质量是怎么提升的

单纯调 OCR 参数提升有限，真正拉开差距的是识别前和识别后的处理：

| 环节 | 做法 | 效果 |
| --- | --- | --- |
| 渲染分辨率 | 按目标宽度 2200px 渲染页面再识别（原来 1600px） | 小字与中文识别率提升 |
| 图像预处理 | 灰度化 + 对比度拉伸（只对发灰的扫描件生效） | 灰底扫描件更清晰 |
| 版面模式 | 可选 自动 / 单栏正文 / 多栏复杂版面（Tesseract PSM 3/6/1） | 书页用单栏模式更干净 |
| 结构化输出 | 取 Tesseract 的 TSV，直接用引擎给出的 块/段/行/词 层级 | 段落边界不再靠猜 |
| 文本清理 | 合并中文字间空格、全角标点去空格、西文断行连字符合词 | `自动 化 测试` → `自动化测试` |
| 版面过滤 | 贴页边 + 极短 + 极窄的词视为页眉页脚剔除 | 去掉了混进正文的 `J`、`BB` 这类杂质 |
| 文本层优化 | 相邻中文词块合并成一个 span，西文词后补空格 | 划词得到 `书的` 而不是 `书 的` |

识别结果里会显示置信度（0–100），换语言或换版面模式后可以对比着挑效果最好的。

注意：首次识别要下载语言模型（英文约 10MB，中英混合约 30MB），之后浏览器会缓存；
识别只在你要求的那几页发生，不会自动跑整本。

阅读器本身不绑定某个翻译服务，右上角「翻译设置」里可以切换：

- **MyMemory**（默认）：免费、免密钥，有每日额度，适合先跑通流程。
- **OpenAI 兼容接口**：填 Base URL + Key + 模型，质量明显更好。OpenAI、DeepSeek、以及本地的
  Ollama / LM Studio 都走这个协议。

本地免费方案：先跑 `ollama serve`，Base URL 填 `http://localhost:11434/v1`，Key 随便填，
模型填 `qwen2.5:7b` 之类。

译文会按原文内容缓存到本地，同一段不会重复翻译、不会重复扣费。EPUB 只翻译你看得见的部分
（前后两三屏），所以打开一本厚书不会一上来就把整本翻完。

## 已知限制

- **扫描版 PDF**（整页是图片、没有文字层）**内置了 OCR**，见下一节。
- **双栏论文**的段落合并是启发式的，偶尔会把两栏串到一起；对照侧栏里能看出并手动忽略。
- MyMemory 有每日额度，用完了会提示，切换成自己的接口即可。
- PDF 的对照不做重排（重排代价高、效果差），所以 PDF 是「侧栏逐段对照 + 悬停气泡」，
  EPUB 才是段落内嵌对照。
- 依赖（pdf.js / epub.js / jszip）默认都从 CDN 加载，每个库都配了多个源自动降级；
  全都拉不到时，书架顶部会显示红色的失败详情。

## 开发

改完代码后跑这两个脚本，能挡住大部分低级错误：

```bash
node check-syntax.mjs      # 内联脚本语法 + 引用的元素 id 是否存在
node test-paragraphs.mjs   # 用合成数据验证 PDF 的段落合并规则
```

`check-syntax.mjs` 把 `index.html` 里的内联模块抽出来交给 `node --check`；
`test-paragraphs.mjs` 从 `index.html` 里把 `extractParagraphs` 抽出来，用模拟的 pdf.js
文本项测单栏 / 双栏 / 缩进 / 页码等排版情况——这段是启发式规则，改坏了不报错，只会让对照变乱。

### 附带：Codex 桌面端界面语言诊断

```bash
node check-codex-ui-lang.mjs
```

用来判断 Codex 桌面端「界面主体」为什么不是中文。它检查本地 `localeOverride`、
statsig 功能开关 `enable_i18n` 的初始化情况、以及应用服务端请求的状态分布，并给出判定与下一步。

结论（来自应用自身代码与日志）：界面多语言由服务端灰度开关 `enable_i18n` 控制，客户端默认 `false`；
开关数据源 `https://ab.chatgpt.com/v1/initialize` 失败时，界面固定为内置英文，
本地 `[desktop].localeOverride` 只是偏好、会被忽略。顶部原生菜单不受这个开关影响（跟随系统语言）。

### 附带：把 Codex 数据/运行时目录迁到 D 盘

```bash
node migrate-codex-data.mjs            # 预演：只打印将要做的事，不改任何文件
node migrate-codex-data.mjs --apply    # 执行（必须先完全退出 Codex）
```

用**目录联接（junction）**把 7 个「数据 / 运行时」目录实际搬到 `D:\tools\codex\`，原路径保留为联接：
路径不变、`config.toml` 不变、环境变量不变（不使用 `CODEX_HOME`），程序无感。

| 原路径（保持可用） | 实际搬到 | 体积 |
| --- | --- | --- |
| `~\.codex\.sandbox-bin` | `D:\tools\codex\sandbox-bin` | 310 MB |
| `~\.codex\.tmp` | `D:\tools\codex\tmp` | 105 MB |
| `~\.codex\.sandbox` | `D:\tools\codex\sandbox` | 3 MB |
| `%APPDATA%\Codex` | `D:\tools\codex\appdata-Codex` | 169 MB |
| `%LOCALAPPDATA%\Codex` | `D:\tools\codex\localappdata-Codex` | 6 MB |
| `~\.codex\skills` | `D:\tools\codex\skills` | 0.4 MB |
| `~\.codex\plugins` | `D:\tools\codex\plugins` | 1 MB |

程序本体（`%LOCALAPPDATA%\OpenAI\Codex`，637 MB）与状态库（`config.toml`、`sessions`、`plans`、`*.sqlite`）原地不动。
回滚：`node migrate-codex-data.mjs --revert <名字> --apply`，或 `--revert-all --apply`。

应用更新时若把某个目录重建为真实目录（替换掉联接），D: 上的副本会变成孤儿；脚本在预演时会报告这种情况，
提示先删除 D: 上的旧副本再重跑迁移。

### 金丝雀测试：判定 MSIX 打包应用的那两份 AppData 哪份是活的

Codex 是 MSIX 打包应用，同一份数据会有两份：真实路径 `%APPDATA%\Codex`（以及 `%LOCALAPPDATA%\Codex`）
与虚拟化副本 `%LOCALAPPDATA%\Packages\OpenAI.Codex_2p2nqsd0c76g0\LocalCache\{Roaming\Codex,Local\Codex}`。
脚本默认**不迁移、不删除**它们，只在预演时报告两份的文件数、体积与最近改动时间。

要确定哪份是活数据，做一次可完全回退的金丝雀测试：

1. 完全退出 Codex；
2. 把 `%APPDATA%\Codex` 改名为 `%APPDATA%\Codex.bak-<日期>`（同卷改名，秒级完成）；
3. 启动 Codex，正常用几分钟：改一次设置、发一条消息、看会话列表；
4. **一切正常** → 说明应用用的是 `Packages\...\LocalCache` 那份，旧目录是死数据，可直接删除回收空间；
5. **出现异常**（设置/登录态丢失、侧栏空白等）→ 关掉 Codex，把 `Codex.bak-<日期>` 改回 `Codex`，零损失；
   同时这也证明真实路径才是活数据，改用它作为迁移目标：`node migrate-codex-data.mjs --include-msix --apply`。

`%LOCALAPPDATA%\Codex`（6 MB）可对同样步骤处理，收益很小，可选。

安全性细节：

- **默认预演**，只有 `--apply` 才动手；每个目录都是「复制 → 校验文件数与字节数 → 原路径改名 `.__migrating` → 建联接 → 复核 → 删暂存」，建联接失败会自动还原。
- 上次中断若留下 `*.__migrating` / `*.__reverting` 残留，脚本会在预演时列出、并在 `--apply` 时先清理它们（释放 C: 空间）。
- 删暂存失败（文件被占用）不会中断迁移——联接已经生效，脚本只提示稍后清理。
- 若进程检查**查不到结果**（例如在 Codex 自己的终端里运行，进程查询被限制），执行模式会**拒绝运行**；请在 Windows Terminal / PowerShell 中运行，确认已退出时可用 `--force` 跳过该检查。
- 若 `USERPROFILE` / `APPDATA` / `LOCALAPPDATA` 为空（沙箱终端常见），执行模式同样**拒绝运行**并打印这三个解析值——否则会把真实目录误判成"不存在"而静默跳过。
- 联接指向的比较会忽略尾部反斜杠、`\\?\` 前缀与大小写（Windows 读出的联接常带尾斜杠），避免误报"校验失败"。

### 本地服务器与诊断

```bash
node serve.mjs        # http://127.0.0.1:8000/index.html
```

它比 `python -m http.server` 多了两件事：响应 `no-store`（改完刷新就生效），以及收集页面回传的诊断。
页面里用 URL 参数可以主动触发自检：

| 参数 | 作用 |
| --- | --- |
| `?diag=1` | 把书架里每本书解析一遍（PDF 取页数、EPUB 取书名/章节数），结果写入 `diag.log` |
| `?open=<bookId>` | 自动打开某本书，9 秒后上报渲染结果：适配器类型、段落数、译文框数量等 |
| `?bi=always` | 与 `open=` 配合，自动打开中英对照 |
| `?ui=1` | 检查外观/划词气泡等控件的接线是否正常 |
| `?ui=2` | 用合成事件模拟 Ctrl+滚轮、滚轮翻页、拖动侧栏，验证交互确实生效 |
| `?goto=<页数>` | 与 `open=` 配合，打开后跳到指定页 |

诊断结果可以在 <http://127.0.0.1:8000/diag-log> 查看，或直接看仓库根目录的 `diag.log`。
`diag.log` 是运行时产物，可以随时删。

`src/`、`package.json`、`vite.config.ts` 是最早那版 React/Vite 脚手架，当前 `index.html`
已经不走构建流程，这些文件暂时没有用到。
